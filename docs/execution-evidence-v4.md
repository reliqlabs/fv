# Execution evidence v4

Status: normative contract for the opt-in `fv-evidence-run/v4` producer and its consumers. This document specifies behavior; it claims no implementation or exercised evidence. RFC 2119 keywords apply.

## Scope and compatibility

V4 adds declared deterministic sharing, preflight, execution checkpoints, selective resume, dependency-scoped source freshness, and bounded scheduling. It preserves every required logical claim/tool association. An execution is a physical producer invocation. A slot is one claim's required association with that invocation. Sharing reduces invocations, never slots, claim definitions, observations, bounds, or final gate scope.

The compatibility posture is established. Calls without `schema_version` use the existing factory's v3 branch unchanged. V3 retains its whole verified-input snapshot, conjunctive cohort verdict, unique claim-owned raw artifacts, no partial cohort reuse, binding modes, evidence-class compatibility, and unwaived-assumption rules. V4 MUST NOT turn a v3 record into an execution checkpoint, copy its log into a new invocation, or rewrite prior reviews. V3 artifacts remain readable only under their existing contracts.

V4 data lives below `.fv/evidence/v4/`, which is already inside the structural evidence exclusion. It does not replace `.fv/evidence/records/<claim_id>.json`. A consumer MUST dispatch on the exact schema version before unwrapping fields. Unknown versions, mixed v3/v4 fields, and a v4 record offered to a v3-only consumer fail closed. V4 MUST NOT emit a v3-shaped primary-command projection to obtain acceptance from an older gate. The ledger envelope's existing recognized versions and meanings do not change; v4 consumers discover the v4 run manifest explicitly.

## Invariants

- S1: Each policy slot exists exactly once in the expanded plan and in the full final assessment, including missing work after failure or selection.
- S2: Raw bytes have one immutable execution owner. Multiple slots may reference that owner only when the reviewed policy explicitly shares the same fixed recipe and their complete execution identity matches.
- B1: Execution PASS requires a real completed invocation, zero exit status, the prescribed marker, matching clean endpoints, durable complete artifact/history and closed ownership, under the declared operational/cache/store assumptions. Claim PASS also requires its own observations, classes, tool/dependency coverage and no unsuperseded failure barrier.
- B2: Stale, corrupt, cancelled, unrun or malformed work cannot become PASS through resume, selection, matching bytes or a weaker class; a later execution or observation failure blocks pre-failure successes.
- T1: First observed failure stops new dispatch. Durable execution/history precede claim publication and further dispatch using that slot; in-flight work is accounted for.
- T2: Recovery never steals live/indeterminate ownership. Detected endpoint drift invalidates work. Continuous nonmutation and build-cache correctness are declared assumptions, not conclusions from endpoint equality.

## JSON and path grammar

All object fields in the shapes below are REQUIRED unless marked `?`. An absent optional field takes only its stated default. `null` is different from absence. Unknown fields, duplicate JSON object keys, duplicate IDs, nonfinite numbers, noninteger numbers, and integers outside `0..9007199254740991` are errors, except a signed integer exit code may be in `-9007199254740991..9007199254740991`. Strings contain Unicode scalar values; lone surrogates and invalid UTF-8 are errors. Hashes are `sha256:` followed by 64 lowercase hexadecimal digits. UUIDs are lowercase canonical UUID v4 strings generated by the actual producer. UTC times are `YYYY-MM-DDTHH:mm:ss.sssZ`; timestamps and UUIDs do not enter reusable execution keys.

`Path` means a repo-relative POSIX path with no empty, `.` or `..` components, backslash, control characters, leading `/`, or leading `~`. `Cwd` is `Path` or `.`. Directory prefixes may have a final `/`; they use the existing verified-input component-boundary matching rule. All traversed source, policy, output, and artifact path components MUST be non-symlinks and remain within the real project root. Source paths MUST be regular files. Output files MUST have one link, and distinct artifact paths MUST NOT alias the same `(st_dev, st_ino)`. IDs use `[A-Za-z0-9][A-Za-z0-9._-]*`; evidence tool IDs retain `[A-Za-z0-9][A-Za-z0-9._:+/-]*`. Commands are nonempty arrays of nonempty NUL-free strings. No shell parsing, expansion, or argv normalization is permitted.

### Canonical bytes

Define `C(value)` recursively:

1. Objects use `{`, their keys in ascending unsigned UTF-8 byte order, `:`, and comma separators, then `}`. Arrays retain their given order and use `[` and `]` with comma separators. There is no whitespace or trailing newline.
2. Strings use double quotes. U+0022 becomes bytes 0x5c 0x22; U+005C becomes bytes 0x5c 0x5c. U+0000 through U+001F use lowercase six-byte \u00xx escapes. No short escapes are used. Every other scalar, including slash/U+2028/non-ASCII, is emitted directly as UTF-8 with no Unicode normalization.
3. Integers use decimal digits without leading zeros; zero is `0`. Boolean and null tokens are `true`, `false`, and `null`.

`H(bytes) = "sha256:" + lowercase_hex(SHA256(bytes))`.

`D(label, value) = H(UTF8("fv-evidence-v4/" + label) + 0x00 + C(value))`.

This is a deliberately restricted JSON encoding, not JavaScript `JSON.stringify` or Python's default `json.dumps`. Files may be pretty-printed for storage, but identities use parsed values encoded by `C`; raw input/output file hashes use exact bytes. The canonical bytes of `{"z":null,"a":"é\n"}` are `{"a":"é\u000a","z":null}` encoded as UTF-8. The byte hash of an empty file is `sha256:e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855`; empty arrays and empty files are different inputs.

Arrays that represent sets MUST be unique and sorted by UTF-8 bytes: IDs, paths, prefixes, resources, environment names, accepted digests, and toolchain dependencies. Object arrays representing sets sort by their identifying field. Platform pairs sort by (os,arch). Definition/source/attachment files sort by path; environment entries by name; descriptor toolchain entries by id; members by (claim_id,slot_id). Policy records, their executions, recipes, toolchains, preflight, version_contains and all argv arrays preserve reviewed order. Plan/work arrays preserve expanded policy order; claim files preserve policy record order. Observation arrays preserve request slot order. Consumers reject noncanonical set order instead of silently changing policy meaning.

JSON number tokens MUST use signed decimal integer spelling, with no fraction, exponent, leading zero or negative zero. This lexical restriction is checked before converting numbers, so JavaScript and Python cannot disagree on 1e0 or -0. Only exit-code fields may be negative.

This grammar applies to v4 objects and observation summaries. Incorporated collector attachments keep their existing exact JSON/number/time schemas, including arbitrary-precision nanosecond integers; hash their exact bytes with H and validate them using their original validators. Never round an embedded collector integer through a JavaScript number or reserialize a child report through C. An observation response references the retained report/attachments and returns safe count/status/hash summaries rather than copying its entire large-number report. All original nested evidence remains available to the portable checker.

## Reviewed execution policy

The producer reads a regular source file, normally `.fv/execution-policy.json`. It cannot accept caller-provided recipes or weaken reviewed policy fields.

```text
Policy = {
  schema_version: "fv-execution-policy/v1",
  policy_id: ID,
  verified_inputs: Path,
  intent_path: Path,
  manifest_path: Path,
  definition_files: Path[],
  environment: {
    mode: "sanitized",
    platforms: [{os: string, arch: string}],
    inherit: string[], set: {<environment name>: string}, identity: string[]
  },
  toolchains: ToolDeclaration[],
  preflight: Check[],
  claim_checker: Check,
  recipes: Recipe[],
  records: PolicyRecord[],
  jobs: {default: 2, max: positive integer},
  trust_assumptions: TrustAssumptions
}
TrustAssumptions = {no_concurrent_mutation:true,
  build_cache_integrity:"upstream-build-system",
  retained_history_integrity:"trusted-producer-store"}
Check = {
  id: ID, command: string[], cwd: Cwd,
  resources: string[], toolchain: ID[], timeout_seconds: positive integer | null
}
ToolDeclaration = {
  id: ID, kind: "executable" | "file" | "tree",
  locator: Locator, version_command: string[] | null, version_cwd: Cwd | null,
  requires: ID[], accept: {sha256: Hash[], version_contains: string[]}
}
Locator = {mode: "command", value: string}
        | {mode: "path", value: string}
        | {mode: "command-relative", value: string,
           parent_levels: integer, subpath: Cwd}
        | {mode: "adapter", value: "python-runtime" | "quint-backends"
           | "cargo-toolchain" | "kani-toolchain" | "lean-toolchain"
           | "darwin-native" | "node-toolchain", cwd: Cwd, subject: string[]}
Recipe = {
  recipe_id: ID, command: string[], cwd: Cwd,
  evidence_class: Class, pass_marker: nonempty string | null,
  timeout_seconds: positive integer | null,
  determinism: {mode: "fixed" | "distinct", rationale: nonempty string},
  source_closure: {
    mode: "prefixes" | "verified-inputs", prefixes: Path[], basis: Path[]
  },
  toolchain: ID[], resources: string[], exclusive: boolean,
  bounds: {samples: positive integer | null,
           max_steps: positive integer | null, seed: string | null},
  attestation: null | {
    path: Path, pointer: string, validation: "collector-transitive"
  },
  build_cache:null|{mode:"upstream-integrity",system:"cargo"|"lake"|"node"|"replay",
                    configuration:Path[],resources:string[]},
  ownership_protocol:null|"dossier-quint-private-pipes/v1",
  retained_environment:string[]
}
PolicyRecord = {
  claim_id: ID, required: boolean, evidence_class: Class, scope: nonempty string,
  executions: [{slot_id: ID, recipe_id: ID, tool: ToolID,
    observation_binding: {path: Path, pointer: string}}]
}
Class = "code-enforced" | "proof-discharged" | "bounded-checked"
      | "test-witnessed" | "conformance-tested"
```

`claim_checker.id` identifies the observation validator, not an evidence tool. `jobs.max` MUST be at least two. The default is two; callers may request one or another positive bound up to `max`. A larger bound changes scheduling only. A timeout is enforced without changing the recipe's argv or proof bounds. `null` means no producer-imposed timeout. Bounds repeat the actual recipe's declared bounds and MUST agree with argv and incorporated definitions; they cannot replace missing argv options or silently introduce a different seed.

`verified_inputs` MUST be `.fv/verified-inputs.txt`. `intent_path` MUST equal the dispatch-resolved canonical target. `manifest_path` MUST be `.fv/obligations.json`. `definition_files` contains every incorporated claim, recipe, dependency, observation, activation, and checker definition, including the source of `claim_checker`; these files, the policy, intent, manifest, and dispatch configuration are mandatory binding inputs even when an include list omits them. Each JSON pointer uses RFC 6901, resolves to an existing object or array, and is interpreted by the declared checker. The whole referenced file is hashed. An empty observation object is legal only when the incorporated contract genuinely has no additional named observation for that slot. Missing pointers never mean no observations.

Records MUST agree with the canonical manifest on IDs, required status, obligation kinds, dependency closure, and `required_evidence` coverage. The project checker MUST check incorporated recipe equality and the complete activation boundary, not merely compare this policy to itself. A policy may describe a reviewed assurance selection; selection is not permission to call it full activation. All policy records enter the full policy verdict. The full canonical merge/activation gate additionally retains all canonical required claims, including those outside such an assurance selection. Focused development checks remain separately labeled.

### Sharing and ownership

A fixed recipe owns one physical execution slot in the expanded plan, regardless of the number of referencing claims. A distinct recipe expands to one physical slot per `(claim_id, slot_id)` association, even if commands and output are identical. `slot_id` is unique within its claim; tool IDs are unique within each claim, as in v3. A recipe with no members is an error. Sharing by matching output hash, evidence class, command basename, or tool name is forbidden.

A fixed rationale MUST justify deterministic replay of the complete operation under the declared seed, source/tool/environment closure and bounds. An unclassified or nonfixed-random repetition is distinct. A random test without a fixed seed does not become deterministic because one run happened to pass. Claims may use different named observations of the same fixed execution; each observation check remains separate. Collector output that embeds claim/subject ownership, replay runs, and resource-sensitive operations are distinct unless their complete reviewed contract explicitly supports sharing. No seed dropping, sharding, model rewriting, command combining, or changing sample/step counts is allowed by this format.

The immutable execution artifact owns its stdout, stderr, raw log, nested collector attachments, invocation identity, and result. Claim records only reference that artifact. Referencing the same artifact for a different execution key or for an undeclared distinct slot is an error. Two executions may independently produce identical bytes; neither may borrow the other's file. Artifact-directory ownership, hashes, recorded descriptors, and policy membership are checked together.

## Inputs and source closure

V4 retains the existing verified-input parser, nine structural output exclusions, and UTF-8 path ordering. It takes a complete selected candidate inventory using `git ls-files --cached --others --exclude-standard -z`, plus mandatory binding inputs. It checks git status with `--porcelain --untracked-files=all -z`; staged changes, deletions, renames, selected untracked files, and worktree modifications are dirty. Both paths of a rename count. Cleanliness covers the entire selected input set, not just a recipe's narrower closure.

V4 rejects selected gitlinks/submodules, missing tracked files, symlinks at any path component, nonregular files, unsafe names, and duplicate/aliased source files. V3's existing handling of gitlinks and tracked deletions remains unchanged. A submodule needs a reviewed complete source enumeration before v4 can cover it; it cannot disappear from the closure by being a directory. Policy-required prefixes and basis files must exist and be covered; ignored dependency files explicitly consumed by a tool must be declared as mandatory binding files or included in the appropriate tool/config attestation.

```text
SourceFile = {path: Path, hash: Hash, size: integer, executable: boolean}
InputState = {
  verified_inputs_policy_hash: Hash,
  inventory_hash: Hash, source_snapshot: Hash, clean: boolean,
  files: SourceFile[]
}
Closure = {
  mode: "prefixes" | "verified-inputs", prefixes: Path[], basis: Path[],
  files: SourceFile[], hash: Hash
}
```

`files` sorts by path. `executable` is true if any POSIX execute bit is set; nonexecute permissions, inode numbers, mtimes, and absolute worktree paths are not source identities. `inventory_hash = D("inventory", [{path, executable}, ...])` over all `InputState.files`. The whole `source_snapshot` uses the unchanged v3 path + NUL + lowercase content SHA-256 hex + LF concatenation over all selected and mandatory binding files in UTF-8 path order. `verified_inputs_policy_hash` hashes exact policy-file bytes; if the file is absent, hash the canonical parsed default policy with `D("verified-inputs-default", {mode:"exclude",prefixes:[],structural:<the nine existing prefixes in their existing order>})`. Missing other mandatory files is an error.

A prefix closure is the complete transitive source/config dependency set selected by those prefixes, plus every basis file and common binding input. `basis` names the reviewed dependency analysis or machine-readable dependency description that establishes completeness. An empty or uncertain basis MUST force `mode:"verified-inputs"`, empty prefixes, and the whole verified set. A validator cannot infer closure completeness from a successful command. New dependencies require an updated reviewed closure before reuse. `Closure.hash = D("source-closure", {mode,prefixes,basis,files})`.

The path inventory is global even with a prefix closure. Input additions, deletions, renames, and executable-bit changes invalidate all old execution keys. Content changes outside a proven prefix closure can reuse an execution only after the new full inventory is validated and clean. Symlinks and dirty state always reject reuse. Content changes inside the closure change its hash. Unknown dependency closure falls back to whole verified inputs.

Capture InputState before any version probe, preflight subprocess, collector lookup or evidence command. Recompute it after preflight and immediately before and after every evidence command and observation-checker call. Require equal clean endpoint states, common bindings and relevant tool/environment/cache-selection identities, including content outside a recipe's closure. Detected drift invalidates affected work and halts dispatch; a final matching clean scan is required for publication. Earlier immutable checkpoints remain subject to the failure-history rules below.

### Operational assumptions and generated build caches

Policy.trust_assumptions declares operational trust, not facts proved by endpoint hashing. no_concurrent_mutation excludes uncoordinated source/tool/configuration/cache writers throughout the invocation, including editor save/undo, package replacement, timestamp manipulation and other build processes. Approved tools/probes must not alter verification inputs; only declared generated-output namespaces may be written under their held resources. Endpoint scans detect net endpoint drift. They cannot detect an A-to-B-to-A edit entirely between scans, and they do not establish a continuous immutable OS view. V4 adds no sandbox or universal watcher. A known violation is ERROR even if final bytes match; absence of an observed violation is not proof that no writer existed. Local and portable reports disclose this assumption.

A build recipe may execute generated products selected by Cargo, Kani, Lake, Node or the existing replay collector. It does not claim a fresh compilation. build_cache_integrity trusts those declared upstream build systems, their selected cache namespaces and their freshness metadata to supply products built from the applicable bound inputs by the bound toolchain. This excludes corrupt/poisoned caches, stale binaries accepted through preserved/backdated timestamps, manual product replacement and uncoordinated cache mutation. Source/tool hashes alone do not prove that the selected executable or proof object was compiled from those hashes. This remaining trust must be visible in the verdict provenance; changing a recipe to clean/rebuild, a new isolated namespace or a content-addressed build system is not authorized here.

Recipe.build_cache is null only when it consumes no generated build products. Otherwise its source configuration paths enter the mandatory closure, and every declared build-cache resource must be in Recipe.resources. Resolve effective target/output/package-build/transformation/compiler-cache namespaces using the actual selected command, configuration and semantic environment. Do not assume target/ or .lake/build when the effective selection differs. Installed immutable distributions remain tool inputs; adapter enumeration excludes generated-product namespaces identified by this cache contract and attests their selection separately. Generated products themselves are not represented as independently source-correct tool bytes.

```text
BuildCacheIdentity = null | {
  system:"cargo"|"lake"|"node"|"replay",
  configuration:[{path:Path,hash:Hash}],
  namespaces:[{role:ID,kind:"selected-path"|"producer-fresh",identity_hash:Hash}],
  integrity:"upstream-build-system"
}
```

Configuration hashes are exact file-byte H and sort by path. Namespaces sort by unique role. For selected-path, identity_hash is H(UTF8(the actual canonical effective namespace path)); primary records do not disclose raw inherited path values. The roles distinguish Cargo target/incremental/compiler caches, Lake project/package builds, Node transformations/builds and replay work as applicable. For producer-fresh, identity_hash = D("cache-namespace-fresh",{recipe_id,role}); that kind is permitted only for an existing incorporated collector's fresh/empty-work guarantee, validated against its original retained report. It does not introduce a new namespace override or change argv. Local reuse revalidates cache selection/configuration under the stated integrity assumption, not every mutable generated byte. Portable validation checks recorded selection provenance, the declared configuration/resources and trust disclosure; it never asserts a fresh or independently content-bound compilation.

## Sanitized environment and toolchain attestation

The semantic child environment is exactly inherit union set; set wins and identity names that same union. Names use [A-Za-z_][A-Za-z0-9_]*. Unlisted ambient values cannot reach it. Every value source is reviewed as public/nonsecret; credentials, tokens, cookies, private keys, secret-bearing configuration and ambient environment capture are forbidden. Absent inheritance stays absent; policy literals are public. Primary EnvironmentIdentity records inherited values only as hashes. Two bounded exceptions apply: the producer-created reserved control-only FD variable for ownership_protocol, and Recipe.retained_environment public names in unchanged incorporated collector reports. The FD value is never inherited, caller-supplied, a semantic seed/input or part of EnvironmentIdentity; recipe protocol binds its reviewed meaning. It may appear only as existing transport provenance.

retained_environment is a unique sorted allowlist, empty for noncollectors and permitted only with an incorporated attestation contract whose original schema emits those names. Review each existing emitted value source, including collector-derived public child paths/configuration. Preserve exact original report/attachment bytes and validators; do not redact or change primary identity to raw values. The Dossier replay exception covers exactly its existing reviewed ENV_KEYS fields, not arbitrary ambient variables. A name allowlist never authorizes secret values or expansion to a general environment dump; secret capture must be prevented before dispatch, and a detected violation is ERROR with no admissible evidence. V3 reporting/transport remains unchanged.

```text
EnvironmentIdentity = {
  os: string, arch: string, release: string,
  variables: [{name: string, present: boolean, value_hash: Hash | null}]
}
```

`value_hash = H(UTF8(value))` if present and null otherwise. Identity records sort by name. OS and architecture MUST match a policy platform; release identifies the real producer OS release. Local reuse compares the actual installed environment and platform to the recorded identity. Portable validation compares recorded identity structure/platform to reviewed policy and fixed public `set` values; it does not hash the CI host's environment. Secret-looking variable names alone are not sufficient to classify a value as safe. Public path variables such as PATH/HOME and reviewed tool config/cache paths may be inherited and hashed. Nonpublic config files that affect tools require content-hash attestation without storing their bytes. If a required environment dependency cannot be safely attested, v4 preflight fails.

A command locator resolves using the sanitized child PATH. A path locator accepts an absolute producer path or a repo-relative path; no `~` or environment expansion occurs. A command-relative locator resolves the command's executable realpath, starts at its parent directory, ascends `parent_levels`, and appends `subpath`. Resolution is typed and bounded; no arbitrary discovery script is implied. An executable is invoked through the resolved entry name, preserving rustup/elan argv[0] dispatch, while its real target bytes are attested. File/tree locators MUST resolve to the declared kind.

```text
ToolFile = {path:ToolPath,kind:"file",hash:Hash,size:integer,executable:boolean}
         | {path:ToolPath,kind:"directory"}
         | {path:ToolPath,kind:"symlink-file",target:string,resolved_path:ToolPath,
            resolved_hash:Hash,resolved_size:integer,executable:boolean}
         | {path:ToolPath,kind:"symlink-directory",target:string,
            resolved_path:ToolPath,resolved_hash:Hash}
ProducerLocator = {mode:"adapter",value:"producer-runtime",cwd:".",
                   subject:["fv_evidence_run"]}
ToolIdentity = {
  id: ID, kind: "executable" | "file" | "tree",
  locator: Locator | ProducerLocator,
  digest: Hash, files: ToolFile[], packages: PackageIdentity[],
  version: {command: string[], cwd: Cwd, stdout_hash: Hash, stderr_hash: Hash,
            text: string, exit_code: integer} | null,
  discovery: [{command:string[],cwd:Cwd,stdout_hash:Hash,stderr_hash:Hash,exit_code:integer}],
  system_dependencies: {os:string,arch:string,release:string,
    sdk:{version:string,settings_hash:Hash}|null},
  requires: ID[]
}
```

Single file/executable identities contain one file entry at path:".". Tree identities contain explicit directory entries, including empty directories and each labeled root, plus regular files and separately typed symlink entries, sorted by UTF-8 path bytes. ToolPath is Path or "."; tree resolved_path values name canonical paths inside the declared virtual root set. Preserve the literal UTF-8 symlink target string, but never resolve a producer absolute target path on a portable checker. The producer maps its actual target to resolved_path in the complete recorded manifest. Missing targets, outside roots, ambiguous alias mapping, devices and unreadable entries fail closed.

Traverse ordinary directories within each declared root view, sharing actual-byte hashing for identical physical targets. Do not recurse through directory symlink aliases or flatten their descendants under the alias path; each alias has its own symlink-directory entry. Resolve its canonical target against the deepest declared real directory root that contains it, breaking equal-depth ties by UTF-8 label order. Repeated targets and multiple ordinary root views are allowed; do not invent a filesystem symlink for a duplicate root declaration. Reject cycles through real directory containment and symlink resolution, and reject a cyclic canonical target-hash dependency graph. Consumers use recorded canonical resolved_path entries and the acyclic manifest to reconstruct target hashes without producer absolute paths.

A symlink-file resolves to a regular-file entry; its resolved_hash/size/executable equal that target's fields. A symlink-directory has no file size or executable field. Its resolved_hash = D("tool-directory",{entries:<all proper descendant entries of resolved_path>}), with each descendant path made relative to that directory; preserve its other fields, including canonical resolved_path values. Include directory entries and nested link entries, sort relative paths by UTF-8 bytes, and evaluate nested target hashes in acyclic dependency order. The target directory itself is excluded from entries; an empty directory uses entries:[]. Consumers independently reconstruct this digest from the retained manifest. Link cycles, contradictory hashes, missing canonical entries and flattened alias copies reject.

ToolIdentity.packages contains the source-qualified Cargo package identities below for Cargo/Kani contexts and [] for other families. Sort by the bare package digest. digest = D("tool-content",{kind,files,packages,system_dependencies}). Version probes use exact version_command/version_cwd under the semantic sanitized environment. version_cwd is null iff version_command is null; a null version requires empty accept.version_contains. UTF-8 stdout followed by stderr, trimming only leading/trailing ASCII spaces, CR, LF and tabs, forms text. Nonzero version/discovery status is preflight ERROR. Discovery arrays preserve actual probe order and exact stream hashes; only nonsecret probe identities may be retained. Top-level executable symlinks attest resolved bytes while invocation preserves the entry name.

Include only the applicable installed distribution and exact selected dependency packages, not all HOME, Cargo/Corepack caches or SDK files. Prefix each file path with its root label, deduplicate the same label/path, and sort by UTF-8 path bytes. An owned message is accepted only on that collector's private channel. Duplicate, malformed, oversized (more than 4096 bytes before LF), out-of-order, foreign-parent, wrong-session or uncheckable messages reject without ACK, cancel proven-owned work and leave uncertain ownership indeterminate. On released, use the prior owned identity, verify the original group is terminated, durably record release, then ACK. A reaped or reused PID alone is insufficient. Do not signal a group whose ownership/start/session validation is ambiguous.

The existing wire has no before-Popen event. Therefore keep a collector-lifetime active SpawnWindow from its own pending launch through protocol completion. If collector/producer death occurs between separate-session spawn and owned delivery, its child gate is designed to close without exec, but that fact alone is not evidence that no process survives. EOF, pipe failure, missing registration or a partial message during an abnormal stop makes the window indeterminate. Close it only after approved normal collector completion, complete protocol accounting, proven termination of every registered original group and no unresolved registration window. Otherwise retain ownership and resources until explicit recovery proves all possible gated/unregistered work has stopped. Never claim orphan cleanup merely because directly known groups were killed. The retained OwnershipReceipt records these original observations; portable checking validates their structure/bindings under producer/OS honesty, not by looking up historical PIDs on CI.

Deadlines/cancellation signal only proven-owned groups: SIGTERM, at most five seconds, then SIGKILL remaining proven-owned children, with original collector cancellation grace unchanged. Drain all streams/control messages. A timed-out/cancelled process never PASSes even with a marker. Normal completion requires actual normal exit, all owned groups stopped and all windows closed. A separately declared external service is independently identity-checked and resource-locked, never killed as an owned child. Invalid UTF-8 is ERROR with exact captured bytes retained. Unproven descendant termination keeps resources/ownership indeterminate rather than claiming cleanup.

## Checkpoints, fail-fast and resume

After actual execution stops and streams/control channels are drained, validate/hash its complete files and endpoint identities. A PASS additionally requires closed ownership windows and the declared cache/input/history assumptions. Use unique sibling staging directories on the same supported filesystem. Durably create each new ancestor directory and its entry in the existing parent before acknowledging any descendant publication. Write/fsync every file; fsync every created or modified directory bottom-up, including attachments/bundle subdirectories, empty directories and the staging root. Then atomically rename to the never-before-existing final attempt path under exclusive ownership, fsync its parent and any newly changed ancestor chain. Existing destinations conflict and are never overwritten. Apply this same recursive discipline to execution attachments, observation/check/claim/run files, history/recovered-owner records and owner updates.

Checkpoint acknowledgment occurs only after all required file/directory barriers succeed, under the declared local filesystem/hardware fsync and same-filesystem atomic-rename semantics. Unsupported durability semantics or any barrier error prevents acknowledgment/PASS cache eligibility; no silent weaker storage mode is allowed. A crash can leave staging or an unacknowledged visible final directory. Later readers must validate it and its history accounting; orphan logs, missing/truncated files and unindexed success are not cache entries. The protocol does not claim stronger crash durability than the supported filesystem's stated barriers.

A physical success artifact and execution history event become durable before member observations or later dispatch. Physical checkpoint validity and eligibility for each canonical claim/tool association are distinct: shared bytes/descriptor/history must validate, then that member must satisfy its own observations and cutoffs. Observation FAIL blocks only its selected association; an execution FAIL applies to every recorded member. Neither rewrites prior checkpoint bytes. Retain failure/error/cancellation artifacts/events when storage works. On storage failure return ERROR without invented references and leave PendingResult/ownership unresolved until explicit recovery accounts for it. ### Ordered retained history and failure barriers

Before each actual evidence or observation invocation, durably persist PendingResult in Owner with its original reviewed members and selected claim/slot, so recovery never guesses membership from a changed policy or an irreversible key hash. Append history after the actual result/receipt is durable; clear pending only after its event is durable. Physical events precede observation events. Owner/append mutex serializes global sequence; clocks/UUIDs do not order supersession. Hold the key admission lock through member observations/history. OwnershipReceipt retains all original attempt-scoped direct/hosted registrations, not merely the currently active child list; only real proven group termination assigns terminated_at. PASS requires every retained registration terminated and every window closed. Registration arrays preserve actual registration order. Pending members sort by (claim_id,slot_id) and observations name their exact member; execution pending claim/slot are null.

A first failure stops admission of new evidence recipes and new costly preflight work. ## Bounded concurrency and locking

Admit at most `jobs` evidence recipes at a time. A recipe holds all its declared resources until the process and children stop, output is drained and its execution checkpoint is durable. Resource IDs are reviewed nonempty strings. Same-ID resources serialize, including Cargo target/configuration work, Apalache server/solver access and shared mutable package caches. Acquire a recipe's complete resource set atomically in sorted UTF-8 order; no partial acquire-and-wait deadlock. `exclusive:true` waits for all local in-flight recipes to stop and prevents any other local recipe from admission until it finishes; replay uses exclusivity and its global resource lock. A scheduler may skip a blocked recipe to admit an independent later recipe, retaining policy-order tie breaking. It never changes the exact argv or bounds for throughput.

Use a project publication-owner lock below `.fv/evidence/v4/locks/` to prevent simultaneous runs publishing claim generations, plus execution-key locks and resource locks. Resource locks are global on the producer host under `$XDG_CACHE_HOME/fv-evidence-v4/locks/`, or `$HOME/.cache/fv-evidence-v4/locks/` when XDG_CACHE_HOME is absent. This path must be covered by sanitized environment identity. Lock names are the bare hex of `D("lock-resource",resource_id)`; the same reviewed resource ID therefore serializes across projects/worktrees. Different local lock directories cannot pretend to serialize a shared server or Cargo target. Lock/cache storage symlinks are errors. Owner creation uses exclusive creation, never check-then-create.

## Local cache validation, portable checking and dashboard

Local validation decides whether a real producer invocation may be skipped. It compares current installed transitive tool/configuration bytes, semantic environment, producer implementation, clean endpoint closure/inventory, cache namespace/configuration selection, retained artifact ownership/bytes and complete failure history. It relies on declared upstream generated-cache integrity and no uncoordinated mutation. Version text alone and an old success before a failure cutoff are insufficient.

Portable checking recomputes canonical identities, policy/common/current source closure and global inventory, all artifact/reference/tree/package/history hashes, full claim/tool/dependency coverage, classes, markers, member observations and original child provenance/times. Recorded tool/environment/cache-selection provenance is checked under policy and pins without requiring producer paths or Darwin binaries on CI. It evaluates the complete supplied trusted-history prefix, including later retained failures than the selected run. Clean content-only changes outside a proven closure remain allowed; dirty/inventory/common/closure drift rejects. Endpoint agreement is conditional on nonmutation, generated-product correctness on upstream cache integrity, and history completeness on trusted retention/export. Hashes do not authenticate actual command execution or absent/deleted history. Uncheckable provenance/closure/history is ERROR/INCOMPLETE, never PASS.

A portable report distinguishes binding:"recomputed" and validation:"portable-checker" from validation:"local-producer-cache", and discloses policy trust_assumptions plus history_binding:"retained-store-completeness-assumed". Pinned/unbound modes retain qualified verdicts and never license cache reuse. Every required canonical claim/tool association and retained failure barrier is expanded independently of run selection; genuine required FAIL precedes gaps. Source freshness is endpoint recomputation under nonmutation trust, build products rely on declared upstream cache integrity, and history completeness/nondeletion is a trusted-store/export assumption. Canonical full activation is a separate unnarrowed assessment.

The coverage dashboard may describe schemas, declared classes, slots, execution sharing, observations and stored results. If it does not recompute freshness, it MUST report `binding:"not-recomputed"` and MUST NOT present a stored PASS as fresh/reusable evidence. It must validate v4 shape/reference completeness and class compatibility rather than drop unreadable executions or downgrade v4 to v3. Report logical association counts separately from unique physical execution counts, cache hits and missing/failed/cancelled work. A single shared proof must not inflate the number of actual producer runs or erase an individual failed observation.

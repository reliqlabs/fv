### 1. Resume resurrects a PASS that predates a real failure [severity: serious]
- **Category**: temporal-state mismatch
- **Affected**: `FV/docs/execution-evidence-v4.md:375-379,404,433`; Dossier distinct property-test slots.
- **What's wrong**: Run A earns PASS for C-01's distinct EX-003 slot under key K. Run B uses `resume:false`, executes that same slot under K, and finds a genuine property-test failure. Run C uses the default `resume:true`. The specified search considers candidate PASS artifacts and selects the earliest successful attempt, so A becomes a cache hit without any successful execution after B. Rechecking observations on A's output reproduces A's success and does not address B's counterexample. Retaining B somewhere on disk does not prevent the current claim from becoming PASS. This is especially reachable for the explicitly unseeded, distinct property tests. The clause allowing a historical failure to be superseded by a new actual success does not justify superseding it with an older success.
- **Cite (spec)**: > “Multiple valid attempts for the same key use the earliest successful attempt by `(finished_at,attempt_id)` order after complete revalidation; an attempt's historical FAIL remains retained but does not poison a new successful actual invocation forever.” (`FV/docs/execution-evidence-v4.md:377`)
  > “Required-record FAIL has precedence over missing/error/cancelled records.” (`FV/docs/execution-evidence-v4.md:404`)
- **Cite (intent)**: > “Required FAIL retains precedence over absent evidence, and cancellation or unrun work cannot become PASS.” (`D/docs/intent.md:32`, I12)
- **Fix recommendation**: Define attempt supersession explicitly. A genuine later failure must invalidate eligibility of earlier successes for the same physical slot/key until a later actual execution succeeds under the applicable recovery rule. Preserve the failure and its ordering in local resume and portable assessment. An immutable success artifact can remain stored without remaining eligible.

### 2. Build-cache contents can substitute an old program beneath a fresh source binding [severity: serious]
- **Category**: coverage gap
- **Affected**: `FV/docs/execution-evidence-v4.md:128-151,196-198,208,331`; Cargo/Lake recipes, including `D/.fv/execution-policy.json:1216-1262,1995-2056`.
- **What's wrong**: The contract binds current source bytes and installed compiler/package bytes, but does not define admissibility of mutable generated build products used by those tools. Consider an existing Cargo target directory containing the previously passing property-test executable. Source is changed and committed while its mtime is preserved or backdated, leaving Cargo's existing freshness inputs satisfied. A real `cargo test` can execute the old binary and emit the required test name and PASS marker. All specified source hashes are stable and current, and all tool identities match, yet those bytes were not tested. Hashing the compiler and dependency sources does not bind the executed build product to them. Dossier explicitly ignores `target/` and `proofs/lean/.lake/` (`D/.gitignore:25-30`). The general requirement to include ignored dependencies does not supply a usable rule for outputs that legitimately change during a build: treating them as immutable tool/source inputs instead makes normal builds invalidate themselves.
- **Cite (spec)**: > “`executable` is true if any POSIX execute bit is set; nonexecute permissions, inode numbers, mtimes, and absolute worktree paths are not source identities.” (`FV/docs/execution-evidence-v4.md:145`)
  > “Resolve the rustup/subject/override-selected actual compiler and Cargo, sysroot/target libraries, applicable noncredential Cargo configuration, and exact locked feature/target dependency graph.” (`FV/docs/execution-evidence-v4.md:196`)
  > “A completed execution PASS requires exact before/after source, tool and environment equality.” (`FV/docs/execution-evidence-v4.md:331`)
- **Cite (intent)**: > “Scoped reuse validates current dependency closure, complete tool/environment provenance and each claim-specific observation without changing activation requirements.” (`D/docs/intent.md:25`, I11)
- **Fix recommendation**: Add a generated-build-cache contract separate from immutable source/tool identity. Require a trustworthy content-bound cache, or a reviewed isolated build-output namespace populated for the bound inputs, before accepting build/proof results. State the trust assumption for any retained compiler/build cache and bind the selected cache configuration. Preserve recipe argv and bounds; do not silently add clean/rebuild commands or change the existing v3 path.

### 3. Endpoint scans cannot establish the claimed absence of in-flight edits [severity: serious]
- **Category**: temporal-state mismatch
- **Affected**: `FV/docs/execution-evidence-v4.md:20,145,151,202,331`; `FV/docs/incremental-reverification.md:209-214`; `FV/CONCEPTS.md:270-275`.
- **What's wrong**: A selected file contains A at the pre-scan. During verification an editor replaces it with B, the verifier reads B, and an undo restores A before the post-scan. Git status is clean again. Both recorded InputStates, all content hashes, and the final scan match A. The specified observations cannot distinguish that run from one that read A throughout. The same ABA trace applies to a selected runtime or backend changed and restored between probes. This breaks the unconditional temporal promise while satisfying the prescribed endpoint equality checks. Producer honesty and ordinary OS integrity do not exclude an editor save/undo or package replacement during a long-running verification.
- **Cite (spec)**: > “A source or tool change during an invocation invalidates that invocation.” (`FV/docs/execution-evidence-v4.md:20`)
  > “Recompute it after preflight and immediately before and after every evidence command and observation-checker call.” (`FV/docs/execution-evidence-v4.md:151`)
  > “Every invocation checks the entire input state before and after, so source mutation during an execution invalidates it.” (`FV/docs/incremental-reverification.md:213-214`)
- **Cite (intent)**: > “prior-format evidence, copied logs and historical source bindings cannot be presented as new runs or rebound to changed source.” (`D/docs/intent.md:25`, I11)
- **Fix recommendation**: Execute against an immutable source/runtime view or add an explicit exclusion mechanism covering all writers for the invocation. If the design only detects endpoint drift, state that limitation and its required no-concurrent-mutation trust assumption instead of claiming detection of every in-flight change. File watching without a defined loss/overflow rule is insufficient.

### 4. The native supervisor has no contract for the collector's separate child process groups [severity: serious]
- **Category**: composition failure
- **Affected**: `FV/docs/execution-evidence-v4.md:155,260-262,419-425`; `D/.fv/execution-policy.json:34-73`; `D/.fv/scripts/collect_quint_witness.py:29-30,285-318,350-369`.
- **What's wrong**: The existing Quint collector launches each subject with `start_new_session=True`, outside its own process group. It has a hosted ownership protocol, but only activates it when `DOSSIER_QUINT_OWNERSHIP_FDS` is supplied; its `notify` function otherwise returns without registering the group. Dossier's reviewed environment does not include that variable, and v4 requires the child environment to equal the reviewed inherit/set union. Launch the collector, let it create a separate Quint group, then kill or stall the collector before it forwards cancellation. Signalling the native supervisor's directly owned collector group cannot kill that Quint group. The parent may release resources or leave orphan proof work after cancellation. The spec asserts complete ownership without defining a channel or containment mechanism that reaches this already-existing boundary.
- **Cite (spec)**: > “The child environment is exactly `inherit` union `set`; `set` wins and `identity` MUST name that same union.” (`FV/docs/execution-evidence-v4.md:155`)
  > “Deadlines and cancellation signal only owned groups: send SIGTERM, wait at most five seconds, then SIGKILL remaining owned children and drain stdout/stderr.” (`FV/docs/execution-evidence-v4.md:262`)
  > “Record child ownership when launching and retain it until every child stops.” (`FV/docs/execution-evidence-v4.md:423`)
  Grounding code: > `if self.control is None: return` in `notify` (`D/.fv/scripts/collect_quint_witness.py:313-315`); > `start_new_session=True` (`:358-360`).
- **Cite (intent)**: > “cancellation or unrun work cannot become PASS.” (`D/docs/intent.md:32`, I12)
- **Fix recommendation**: Specify and integrate descendant ownership before enabling these collectors: a gated registration/acknowledgement protocol with durable spawn intent, or an OS containment mechanism that includes separately created sessions. Define any reserved transport FD/environment exception explicitly, distinguish it from evidence-affecting environment identity, and preserve v3 transport behavior. Recovery must account for children that escaped the direct parent group before the parent died.

Specify registry, git and path dependencies and the feature/target selection. Do not substitute the ambient Cargo compiler graph for Kani's graph.

### 7. Directory symlinks have no defined ToolFile identity [severity: serious]
- **Category**: under-specification
- **Affected**: `FV/docs/execution-evidence-v4.md:169-188,194-200`.
- **What's wrong**: The tree contract accepts symlinks whose targets stay inside an attested root, but every symlink must carry `resolved_hash` and `resolved_size` for its target bytes. A directory symlink has no file byte stream or specified size. For example, an installed Node dependency tree may contain `node_modules/pkg -> ../packages/pkg`, with the target explicitly included in the adapter roots. One implementation can follow and flatten the directory, another can record only the link and canonical target tree hash, and another can reject it. The spec supplies no choice, no directory-target digest domain, and no rule for distinguishing an allowed repeated target from a cycle. These are routine installed package/framework shapes, and the portable consumer cannot independently derive one canonical manifest from the present rules.
- **Cite (spec)**: > `| {path: string, kind: "symlink", target: string, resolved_hash: Hash, resolved_size: integer, executable: boolean}` (`FV/docs/execution-evidence-v4.md:171-172`)
  > “Symlink target strings and resolved target bytes are included; a target must stay inside the declared tree or an explicitly included adapter root. Cycles, broken links, devices and unreadable entries reject attestation.” (`FV/docs/execution-evidence-v4.md:188`)
- **Cite (intent)**: > “complete tool/environment provenance” (`D/docs/intent.md:25`, I11)
- **Fix recommendation**: Specify directory symlink handling separately from file symlinks, including canonical target identity, traversal, duplicate targets and cycle detection. Define portable root-relative targets where producer absolute paths cannot be resolved on the checker host. If a particular directory-link shape is unsupported, name it and confirm that required installed distributions have a supported representation.

### 9. The checkpoint fsync sequence does not make nested attachments durable [severity: serious]
- **Category**: edge case
- **Affected**: `FV/docs/execution-evidence-v4.md:291-294,373-375,406`.
- **What's wrong**: An execution owns `attachments/report.json` and `attachments/bundle/blob`. The prescribed algorithm fsyncs every file, then the top-level temporary attempt directory, then renames it and fsyncs its parent. It never requires fsync of `attachments/` or `attachments/bundle/`, nor durable creation of newly created ancestor directories such as the execution-key directory. On a filesystem requiring directory fsync for durable entries, a crash can retain execution.json while losing a nested file name, despite the producer having announced a durable PASS checkpoint. Later validation rejects the corrupt checkpoint, so this is chiefly a crash-recovery/durability failure rather than a justified PASS after recovery. It defeats the promised reusable success and can permanently halt resume on producer-created corruption.
- **Cite (spec)**: > “Write all files plus `execution.json` to a unique sibling temporary directory, fsync every file, fsync that directory, then rename the directory to its final never-before-existing attempt path and fsync the parent.” (`FV/docs/execution-evidence-v4.md:373`)
  > “An execution PASS persists before observation/claim processing or further evidence dispatch.” (`FV/docs/execution-evidence-v4.md:375`)
- **Cite (intent)**: > “Opt-in `fv-evidence-run/v4` may reuse only actual producer-created immutable execution artifacts” (`D/docs/intent.md:25`, I11)
- **Fix recommendation**: Require bottom-up flushing of every created/modified directory in the artifact tree and durable creation of newly created ancestors before acknowledging the checkpoint. Apply the same rule to nested run/claim/observation storage. State the supported filesystem durability assumptions and reject storage that cannot provide them.

### 10. Atomic pointer replacement cannot promise the old pointer after every publication failure [severity: serious]
- **Category**: contradiction
- **Affected**: `FV/docs/execution-evidence-v4.md:373,406`.
- **What's wrong**: `current.json` initially names run A. Publication of B successfully performs the atomic replacement, then the required parent-directory fsync fails with an I/O error. The pointer already names B. The spec nevertheless requires the previous pointer to remain unchanged whenever publication fails. Attempting a rollback does not repair the guarantee: rollback can fail or the process can crash between replacement and rollback. This is a normal failure cut in the prescribed algorithm. Implementers must either violate the old-pointer guarantee or conceal the fsync error. It also leaves consumers without a specified interpretation of a visible new pointer after the producer returns publication ERROR.
- **Cite (spec)**: > “Publish `current.json` by atomic replacement only after its complete immutable run manifest and claim files exist. ... If publication fails, the previous pointer is unchanged and no successful final verdict is returned.” (`FV/docs/execution-evidence-v4.md:406`)
  > “rename the directory to its final never-before-existing attempt path and fsync the parent. Publish only after this succeeds.” (`FV/docs/execution-evidence-v4.md:373`, incorporated publication discipline)
- **Cite (intent)**: > “Required FAIL retains precedence over absent evidence, and cancellation or unrun work cannot become PASS.” (`D/docs/intent.md:32`, I12)
- **Fix recommendation**: Define publication states around the replacement linearization point. Pre-replacement failure may promise the old pointer; post-replacement durability failure must return ERROR and report an indeterminate old/new durable pointer outcome. Consumers must validate whichever complete generation is present and must not treat that pointer as proof that the failed producer invocation completed successfully. If stronger transactional semantics are required, specify an actual commit/recovery protocol instead of an unconditional rollback promise.
